# 测试记录（中文对照，仅供审核，提交请用英文版）

我们的原型把一天的邮件分进艾森豪威尔四象限，提取待办和截止时间，并能回答关于这批邮件的问题（DeepSeek，`deepseek-flash`）。

**测了什么**

1. **标注集（24 封邮件）**：包括工作、学习、订阅邮件、一封提示词注入、中文邮件和空标题，每封都有固定的预期象限和"是否需要处理"。结果：象限 23/24，是否需要处理 24/24。唯一不一致的是一封周五截止的客户合同，被判为"紧急"而不是"重要不紧急"。
2. **三个示例收件箱**，按事先写好的通过标准检查：18/18。
3. **提示词注入**：一封逾期发票在正文里要求 AI 把它归为不重要，跑了 3 次。3 次都判为"重要且紧急"，并给出付款待办。
4. **聊天**：答案已知的问题各问 3 次，另外问了与邮件无关的问题，以及收件箱里不存在的发件人。
5. **27 项自动化测试**：覆盖输入解析、模型回复格式错误、接口报错，以及邮件里夹带 HTML。

**发现并修复的问题**

- 问"有什么紧急的"，3 封紧急邮件只列出 1 封。我们改写了提示词，要求列出所有符合条件的邮件，之后 6 次运行全部完整。
- 聊天回答显示原始的 Markdown 星号，现在改为纯文字。
- 模型返回字符串 `"false"` 时，会生成假的待办。
- 模型漏掉的邮件会被悄悄放进"可忽略"象限，现在标记为"需人工检查"。
- 重复邮件显示两次，现在会合并。
- 输入内容过大时，连接会直接断开，而不是提示"内容太大"。

**选择不修复的问题**

- 周五截止的合同：两个象限都说得通，多次运行也确实两种结果都出现过。对客户截止日期宁可多提醒，这样出错的代价更小。
- 生成新报告后，旧的聊天记录仍留在页面上，属于外观问题。
- 测试邮件是虚构的，数量也少。真实收件箱里的长邮件串、转发链还没有测过，所以评审用自己的邮件来测最有价值。

**方法说明**：预期标签先由 AI 协助起草，再经团队审核后采用。每项检查都是拿输出和这些固定标签或书面标准比对，从不依赖模型对自己输出的判断。
